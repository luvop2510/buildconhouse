# Six-page experience revamp

Assessment and proposed implementation plan · 10 September 2026

BuildCon House should become a consistent, fast workspace where a person can see the next action, complete it with little navigation, and trust the result. The largest gains come from preserving context, improving long-list performance, and making saving and recovery dependable alongside visual refinement.

This is a source-grounded design and engineering plan, not a completed application redesign. The review used three specialist agents for transaction workflows, sales/follow-ups, and backend/data performance. Application source and production data were not changed. “Builder” is interpreted as the sanitary Quotation Builder; “Bathroom floor purchases” means the Sanitary Bathroom Purchases tracker.

Its 235 browser tests mainly exercise unavailable-data states; it explicitly does not establish all successful workflows or real-device performance (`docs/audit-2026-09-05.md:44–46`).
- Current source already has shared breakpoints, safe-area framing, named shared controls, request deduplication/cancellation, quotation autosave, paginated tile product selection, and independently settling Sales Data sections. Retain these foundations.
- Re-run for this assessment: mobile UX contracts (49 assertions), quotation totals/autosave contracts (3 assertions), Purchases contracts, and Sales date-period regressions all passed. These are useful regressions, not measured usability or end-to-end certification.

## One interaction system across all six pages

Keep the existing warm neutral surfaces, ink text, brass accent and restrained status colors. Use one clear page title, a visible business-unit/customer context, a compact search/filter row, the working content, and one primary action. Reserve large display typography for page headings; use readable body text and aligned numeric columns in operational screens.

| Layer | Proposed contract |
| --- | --- |
| Navigation | Role-appropriate destinations, persistent workspace label, meaningful Back behavior, and restoration of search, filters, selected item and scroll position. Never silently move a draft between floors. |
| Working content | Lists show identity, stage/due time, quantity or value, exception, and next action. Expand secondary information on demand. Product identity includes image, brand, SKU, size/finish and unit where relevant. |
| Actions | One primary action per context. Show a small, stable set of secondary actions; put occasional actions in an accessible menu. Confirm stock/order changes with an explicit summary of their effect. |
| Loading | Stable skeleton on first load; retain already loaded content during same-scope refresh with an Updating indicator. Never display previous-floor records while the selected floor changes. |
| Saving | Distinguish Unsaved, Saving, Saved, Failed and Conflict. Retry must preserve input. A server rejection must not become a success toast. |
| Empty states | Distinguish no records, no filter matches, no permission, unavailable data and offline. Each state provides the appropriate next action. |
| Recovery | Restore eligible drafts by account, floor and document; show recovery time/version and let the user choose whether to restore. Stock movements and order confirmation require a current server acknowledgment. |
| Accessibility | Named controls, consistent focus indication, correct selection semantics, labelled fields and persistent errors. Verify modal focus, Escape/Back and focus restoration at runtime; multiple sheet implementations still exist. |
| Motion | Retain short state transitions; avoid delays before accepting input. Respect reduced-motion settings in sheets, skeletons and toasts. |

The root breakpoint contract is already 768 / 1024 / 1366 pixels (`src/design/tokens.ts:165`). Extend it instead of adding arbitrary per-page thresholds. Use actual remaining content width for multi-pane layouts, following `quotationBuilderLayout` in `src/design/responsive.ts:34`.

| Platform/context | Intended behavior |
| --- | --- |
| Phone, including narrow 320–390px screens | One working column; compact header; large named actions; filters in a sheet; an accessible detail screen/sheet; sticky action clear of navigation and the keyboard. Avoid page-wide horizontal scrolling. |
| Tablet portrait | Comfortable touch controls and richer rows/cards; details use a full-height panel when two columns cannot fit. Do not simply enlarge the phone gutters. |
| Tablet landscape | List/editor plus detail/summary when container width permits; collapsible catalog/context panels; simultaneous touch and keyboard support. |
| Desktop | Compact tables or two/three-pane workspaces, persistent summaries and selected-row context; keyboard shortcuts with visible alternatives. Preserve useful density without shrinking touch targets on hybrid laptops. |
| iOS/Android native | Same business rules and task structure; native date/time pickers, keyboard avoidance, hardware Back behavior, safe areas, accessible reading order and optional haptic acknowledgment. Test separately from mobile web. |

Use 44–48px targets for primary touch controls. WCAG 2.2 AA's target-size criterion is generally 24 CSS pixels with specified exceptions; 44–48px is the proposed comfort target, not a claim about that AA minimum. [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)

## 1. Tiles quotation

**Intended flow:** choose customer/project → choose room/area → select tile → enter quantity/coverage and price → review → save/share or convert through the existing order workflow.

Retain the existing phone/tablet card editor, autosave, sticky action and paginated product picker. Improve the connection between product selection, room context, pricing and document review.

- Phone: show room chips and compact line cards; open one line editor at a time. Keep total and Review available above the keyboard/navigation. Keep PDF preview as a separate review mode so editing does not require a scaled paper layout.
- Tablet: show room/line editing beside the running summary when space permits; use a catalog panel for adding multiple tiles without losing the room context.
- Desktop: catalog/search, room-grouped lines and pricing/review summary. Make tax, discount, quantity unit and conversion assumptions explicit.
- Preserve entered coverage/box/piece values and existing calculation rules; show conversions clearly. Any new wastage calculator must be optional and must not silently change existing quotes.
- Customer lookup must expose failure/retry; `TilesDocBuilder.tsx:264` currently swallows lookup errors.
- Profile and virtualize the long editor: it accepts up to 300 lines (`TilesDocBuilder.tsx:65`), while its card editor maps the rows in a ScrollView (`:1745`, `:1779`). Use one list scroll owner with room headers and a footer, or measured chunked editing; do not remove focused fields during editing.

**Done when:** a user can build, reopen and revise a multi-room quote on phone; quantity, discount and PDF totals agree; 300-line editing remains responsive; a failed lookup/save can be retried without losing input; conversion creates the intended order once.

## 2. Sanitary Quotation Builder

**Intended flow:** customer/project → browse products → arrange rooms → adjust quantities/discounts → review → confirm.

Retain serialized autosaves, cached reference data, product media, calculated totals and existing adaptive pane logic. The proposed refinement is a dependable workspace with fewer interruptions.

- Phone: two clear working modes, Products and Quotation; return from the picker to the same room/position. Use a compact bottom summary with line count, total and Review.
- Tablet: catalog beside quotation at sufficient width; a collapsible summary instead of three narrow columns.
- Desktop: catalog + editable room/line canvas + running summary, with keyboard product search and explicit row actions.
- Complete draft recovery. `BuilderContext.tsx:624–635` writes a local snapshot, but review found no corresponding restore flow. Scope storage to account/floor/document, include a version and timestamp, clear it on logout/expiry, and reconcile it with the saved server version. Native recovery needs a platform storage adapter.
- Replace misleading web drag affordances with working reorder controls. `QuotationCanvas.web.tsx:19` supplies no-op drag callbacks while row grips remain visible. Add Move up/down and Move to room across platforms; pointer drag can be a later enhancement.
- Keep save status visible and actionable; expose conflicts if another person edits the same quote. Inspect existing revision/idempotency behavior before adding new fields or protocols.

**Done when:** users can reorder on web and native, switch modes without losing position, recover a newer draft after interruption, and confirm only after the latest valid draft is saved. Verify current price/media rules rather than changing them as part of layout work.

## 3. Bathroom floor purchases

**Intended flow:** find a customer/PO or stock item → understand stage and shortage → receive/move/transfer/dispatch → verify the recorded result.

- Organize the page around operational queues: Needs attention, Ordered, Received/available and Dispatched, using the existing stage model and permissions. Preserve customer/stock distinctions.
- Phone: card shows customer or stock owner, supplier/PO, product identity, stage, outstanding quantity and one next action. The detail view explains the full movement history.
- Tablet: queue and detail side by side when space allows. Keep selected records visible during updates.
- Desktop: sortable table, column priorities, safe bulk selection and a detail panel. Persist filters on return from PO/customer screens.
- Centralize movement forms with consistent source/destination, unit, available quantity, requested quantity, validation and confirmation. Show before/after quantities and partial outcomes for bulk operations.
- Keep existing server pagination, abort handling, floor isolation and stock-concurrency protections. Refresh affected rows and counters after mutations rather than resetting the entire user's working position.
- Name icon-only actions by intent and context, and verify keyboard + touch access to transfer/history controls.

**Done when:** a user can receive part of an order, locate the remainder, transfer eligible stock and dispatch the right quantity across devices; stale stock and concurrent changes produce clear recovery rather than incorrect local totals.

## 4. Tiles order

**Intended flow:** customer requirement → supplier/brand order → receipt/reservation → dispatch → history.

Retain debounced search, request guards, validated quantities, paginated dispatch selection and duplicate-submit protection documented in the September audit.

- Make Customer orders, Brand orders, Inventory and History clear views of the same operation. Keep customer/PO references visible while drilling between them.
- Phone: stage and exception filters, compact order cards and a full-height detail view. Dispatch becomes Select items → Enter quantities → Review → Confirm, with a result/record link.
- Tablet/desktop: table or queue with persistent detail, receiving/dispatch progress, quantity balances and an explicit next action. Optional board views must preserve list/table access for keyboard users.
- Repair accumulated-list rendering. `tiles/orders/index.tsx:192` appends 30-row pages; `TileTable.tsx:266–273` maps every accumulated row in parent-scroll mode. Use list-owned scrolling and virtualization, or keep only one bounded page. Server pagination alone does not bound rendered rows.
- Move history filtering/sorting/paging into bounded backend reads; current history assembles multiple capped collections before slicing (`backend/routes/tile_orders.py:1649–1672`, `:1752`). Preserve stable ordering and traceability.

**Done when:** multiple loaded pages remain responsive, filters do not lose selection unexpectedly, the review shows exact products/units/quantities, and retries or double taps cannot duplicate a stock movement.

## 5. Sales data

**Intended flow:** understand performance → identify the cause or exception → drill into relevant orders/customers → take action.

Keep the existing independently settling sections, honest unavailable states, valid period handling, revenue comparisons, accessible chart selection and floor scope.

- Start with a compact summary: Revenue, comparison period, Collections/outstanding, and exceptions requiring attention. Keep revenue and cash received distinct.
- Phone: summary first, then a selectable detail area such as Sales, Collections, Products or People. Avoid presenting every breakdown as one long mandatory scroll.
- Tablet/desktop: overview plus trend and ranked breakdowns; detail drawers retain period/floor filters. Provide a table alternative and precise values for charts.
- Preserve loaded data on same-scope refresh. `sales-data/index.tsx:128–132` currently clears all sections; a section retry invokes the same eight-request load (`:157–163`). Retry only the failed section and show per-section update/error state. Scope changes must never show the old scope's values under new labels.
- Give workspaces relevant metrics: quantities for Products, due amounts/aging for Collections, pending work for Operations. `OwnerWorkspace.tsx:78` currently can render quantity under an Orders column; explicitly model column labels and units.
- Separate menu expansion from navigation (`WorkspaceSwitcher.tsx:111–115`) to eliminate avoidable intermediate page visits.
- Replace full-order hydration and Python slicing in sales workspaces with projections, database aggregation and bounded paging (`backend/routes/sales_workspace_routes.py:45–53`, `:99–103`, `:128`). Retain the canonical revenue calculation and date semantics.

**Done when:** an owner reaches an explanation for a KPI without losing filters; unavailable data never appears as zero; retrying Brands leaves Customers visible; totals remain correct beyond 10,000 matching orders in test fixtures.

## 6. Follow-ups

**Intended flow:** see the next customer to contact → understand context → call/contact → record outcome → schedule the next action.

Keep due buckets, saved views, priority ranking, document links and the phone SectionList. Bring the actionable queue higher on the page and keep its context beside the detail on wider screens.

- Make My queue, Today, Overdue and Upcoming simple entry points. Each row shows customer, reason, due time, owner and next action. Secondary filters live behind one filter control with an active count.
- Phone: queue → detail → outcome/reschedule, with convenient contact actions. Tablet landscape: queue/detail split. Desktop: compact queue, customer/document context and outcome controls.
- Fix wider-screen scroll ownership as well as preserving the phone list. An outer ScrollView (`followups.tsx:874`) currently contains a non-scrolling SectionList (`:1034–1039`). Give the tablet/desktop queue one virtualized scroll owner and verify bounded mounted rows, preserved selection and scroll position with large datasets.
- Fix false bulk success first. `followups.tsx:598–623` catches each request error and then marks all selected items successful. Return individual outcomes, update successes only, preserve failed selections and show a persistent result such as “8 completed, 2 failed — Retry failed”. Bound concurrent requests or add a purpose-built bulk endpoint.
- Separate list loading from optional information. Bootstrap currently waits on seven dependencies (`:317–328`). On error, the list can remain empty while the UI says all caught up; refresh also unconditionally says Workspace synced (`:349–354`). Give the inbox a real loading/error state and load summaries/configuration independently.
- Guard detail selection: `:364–374` permits slow response A to replace selected detail B. Check request version in success, error and finally; abort obsolete requests.
- Replace the general inbox's truncated local filtering with server-filtered pagination and full-scope counts (`backend/routes/followup_routes.py:436–467`). A search match beyond the initial 1,000 must remain discoverable.
- Use consistent date/time pickers with timezone clarity and presets instead of typed datetime strings. Expose checkbox and outcome selection state to assistive technology.

**Done when:** an optional insights failure leaves the queue usable; failed bulk changes are accurately reported; selecting B never displays A; all matching reminders are discoverable; logging an outcome and rescheduling work with mobile keyboards and assistive technology.

## Full-stack implementation and migration design

Keep Expo/React Native Web, FastAPI, MongoDB Atlas and Supabase. No evidence from this review justifies changing database or frontend framework. Most UX work needs component/data-loading changes, not schema migrations.

1. **Shared frontend contracts:** standard page toolbar, list/detail scaffold, field and validation model, save status, operation result and query-state handling. Reuse existing API GET deduplication, identity/floor invalidation and AbortSignal support (`src/api/client.web.ts:85`, `:158`); extend it rather than adding competing cache layers.
2. **Small payloads and stable paging:** return the fields visible on each list; fetch details on selection. Add cursor paging to the general Follow-ups inbox with server-side filters and stable tie-breaker ordering. Design equivalent bounded paths for tile history and sales records. Counts must describe the full matching scope, not a loaded page.
3. **Purpose-specific aggregate endpoints:** compute sales summaries in Mongo and avoid hydrating full quotations/payment histories for each workspace. Follow-up stats/mission currently reuse 10,000-document reads (`followup_routes.py:77–82`); aggregate or share a scoped computed result. Consolidation must retain independent section failures rather than create another all-or-nothing endpoint.
4. **Mutation results:** standardize per-item success/conflict/failure results and request identifiers. Retain existing stock locks/version checks. Confirm/dispatch operations need replay-safe server semantics; UI button disabling is only one layer. Reuse existing mechanisms wherever available.
5. **Cache policy:** cache stable references with a bounded lifetime; keep active operational data fresh and visibly updating. Keys include identity/permissions, floor and filters. Invalidate affected rows/queries after mutations. Do not put private API responses into a public edge cache.
6. **Optional later projection:** if measured aggregate latency remains unacceptable, introduce daily sales summaries or a unified tile-event read model with watermarks, reconciliation and rebuild tooling. Do not create a new projection before the simpler queries are measured.

### Migration sequence

| Stage | Work and completion evidence |
| --- | --- |
| Inventory | Inspect current indexes, migration state and representative query plans in the intended environment. Existing analytics and follow-up indexes already exist in migrations 0013, 0018 and 0020; avoid duplicate indexes. |
| Define query contract | Specify filters, ordering, pagination consistency and totals. For Follow-ups, due buckets change with time and personalized priority may affect sorting; preserve those semantics before choosing indexed fields. |
| Expand | Add only needed non-unique indexes/optional version or projection fields using the existing idempotent forward-only runner. Verify key pattern, name and options. A proposed index is not automatically the right one for every filter combination. |
| Backfill if needed | Chunk and checkpoint writes; record counts and versions; prove old/new totals and floor membership agree. Index-only/query-only work does not require a record backfill. |
| Compare and switch | Read-compare old/new paths on representative data. Roll out by module with compatible old clients. Keep an application fallback while new paths settle. |
| Retire later | Remove old paths only after parity and latency checks pass. Revert application reads for rollback; do not drop business data or hastily remove additive fields. |

Compound indexes must follow actual filter/sort use and be evaluated for read benefit and write cost. [MongoDB compound index documentation](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-compound/)

The July AGENTS warning about migration 0006 is historical context, not proof of a current outage. Current `backend/server.py:107–122` disables automatic production migrations by default; the September audit reported no pending migrations at that time. A fresh read-only preflight remains necessary before future deployment. No migration was run for this plan.

## Performance and usability acceptance

Measure the current release first with representative, non-production records. Record build, device, network, dataset size, cold/warm state and cache state so comparisons mean something.

| Measure | Proposed release target |
| --- | --- |
| Web loading/interactions/layout | LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at the 75th percentile, segmented by device; measure full navigations and add separate usable-content marks for in-app navigation. |
| Warm task navigation | Locally rendered feedback within 100ms; usable cached content within 300ms, with current-scope refresh visible. These are proposed product targets, not current measured results. |
| Data latency | Initial goal: p95 ≤500ms backend processing for routine lists and ≤1s for summary aggregates at agreed test scale. Measure network round-trip separately and revise with evidence. |
| Lists | No unbounded mounted rows on accumulating order/follow-up lists; responsive typing and sustained scrolling in a release build on a representative mid-range Android phone. Use fixed row layouts only where row heights are genuinely fixed. |
| Drafts and stock writes | No lost acknowledged edits, no false success, no duplicate confirm/dispatch in retry/double-tap tests; conflict messages preserve user input. |
| Task effort | Establish current steps/time with staff, then target at least 25% lower median completion time on repeated quote, dispatch and follow-up tasks without more errors. This is a proposed study goal. |
| Layout/accessibility | Successful tasks at 320, 390, 768, 834, 1024, 1366 and 1440px; keyboard visible; orientation changes; 200% text scaling and zoom; no obscured focused action. |

Core Web Vitals thresholds come from [web.dev](https://web.dev/articles/vitals). Virtualized list tuning should follow the installed React Native version and measured row behavior; use the [React Native 0.81 guidance](https://reactnative.dev/docs/0.81/optimizing-flatlist-configuration).

The current JS budget is 576KiB gzip and checks login, dashboard, follow-ups and purchases only (`scripts/check-web-budget.mjs:12`). Extend coverage to tile documents, sanitary Builder, Tile Orders and Sales Data using a fresh production build. Do not raise the cap to disguise added weight. Keep image dimensions reserved, serve appropriately sized cached thumbnails, and load full-resolution images only on demand.

`src/lib/monitoring.ts:17` currently disables tracing, and performance signals at `:29` are development-only. Add sampled, privacy-preserving route timing and web-vitals measurements, plus durable backend latency/error metrics. Record route templates and performance values, not customer names, quotation contents or query strings.
