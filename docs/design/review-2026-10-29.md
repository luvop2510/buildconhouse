# Design review: floor Today and shared workspace

## Summary

The investigation baseline **needs work**: Today used a sales-analysis composition for a floor work task, repeating charts before the operational queue. The product thesis is a trustworthy showroom handoff: customer, next action, responsibility and recorded progress together. The shared system typography, neutral controls and source-backed charts are useful foundations; another visual-system replacement would create more drift.

This is a source/reference review of the Expo / React Native Web application, not a completed visual audit of every rendered route. The release's browser results and deployment report establish which surfaces actually passed. Unvisited pages, native devices, production network latency and dark appearance remain unverified unless separate evidence says otherwise.

## Investigation findings

### High — Today answered the wrong question

The previous `app/(admin)/dashboard.tsx` rendered `AnalyticsDashboard` when the account could view Sales Data. `DashboardContent` placed sales KPIs, the trend, contribution and business comparison before the floor's task content. Staff arrived at a report when they needed scheduled work and progress. Treating department access as permission for company sales also exposed the wrong viewpoint.

The correction separates operational Today from owner-only Sales Data. Task counts and the work queue lead; a floor-wide account sees permitted financial/workflow context beside it. The backend must enforce the same department/floor boundary as the layout. This follows `layout.md › Visual hierarchy` and `charting-data.md › Best practices`: importance and the user's analytical task determine prominence. [Apple Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [Apple Charting data](https://developer.apple.com/design/human-interface-guidelines/charting-data)

### High — Written design sources contradicted each other

`src/design/README.md` and canonical tokens specified system type, graphite actions and teal focus, while `docs/design/shared-workspace-system.md` still instructed blue focus and the retired Kitchen palette. This is a concrete mechanism for recurring inconsistency: a later page or agent could correctly follow an obsolete document and restore a different visual language.

The legacy document now points to the canonical contract and uses the same measured token pairs. Historical preview palettes remain historical. New work must extend the shared role system instead of introducing another set of local constants. This applies `typography.md › Conveying hierarchy`, `color.md › Best practices` and `icons.md › Best practices` to the existing codebase. [Apple Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [Apple Color](https://developer.apple.com/design/human-interface-guidelines/color), [Apple Icons](https://developer.apple.com/design/human-interface-guidelines/icons)

### Medium — Selected-floor charts repeated information without a comparison

`DashboardContent` previously showed business contribution and a business-unit bar comparison even when only one floor was selected. A 100% self-contribution ring supplies no decision, and a one-row comparison adds controls without useful contrast.

The integration suppresses these panels when no comparable units exist. The remaining trend, entity rows and balance evidence retain purpose. Keep charts for relationships that need explanation; don't fill an available bento cell just to complete a pattern. This follows `charting-data.md › Designing effective charts`. [Apple Charting data](https://developer.apple.com/design/human-interface-guidelines/charting-data)

### Medium — A shared visual language needs component ownership

The source already has `AdminPage`, `PageHeader`, `Overlay`, shared controls, `AppText`, `NavigationTabs`, canonical tokens and a legacy theme adapter. Reimplementing them inside a new page creates different spacing, loading, focus and icon behavior, even if the initial screenshot looks similar.

The acceptance checklist names these boundaries and page families. The sidebar integration retains the same labels and destinations while using neutral selection, one icon family and consistent targets. Final rendered review must verify long labels, text growth, compact navigation and focus. `icons.md › Best practices` and `sidebars.md › Best practices` support consistency and manageable hierarchy. [Apple Icons](https://developer.apple.com/design/human-interface-guidelines/icons), [Apple Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars)

### Medium — Loading polish must reflect actual dependencies

A unified endpoint can reduce request count while still delaying useful work if it awaits every optional aggregate. A generic loading skeleton can also become misleading when a request has already failed. This release's performance review must measure task availability with slow/failed workflow/payment reads and terminal error states, not just count network requests.

The checklist requires primary work to publish independently, section-local retry and immediate removal of old-floor data. It distinguishes fresh loading, refresh, unavailable, empty and success. This applies `loading.md › Best practices` and `accessibility.md › Cognitive`; visible content and controls must remain useful throughout the request. [Apple Loading](https://developer.apple.com/design/human-interface-guidelines/loading), [Apple Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)

## Craft decisions

The design should be remembered for the clarity of its handoffs, rather than a decorative chart style. Keep neutral chrome and spend teal on useful data/focus. Use unequal bento spans only to express the priority of a work queue over its summary. On a phone, preserve reading order and complete task names. Remove a self-comparison chart before adding another visual accessory. These composition choices are product judgment, not Apple requirements.

The user's Salesly reference contributes alignment, grouping and hierarchy. Its marketing runtime and demo content do not belong in operational pages. The current system-font and graphite direction takes precedence over the earlier Inter Tight/blue preview. See [reference decisions in the checklist](interface-acceptance.md#reference-review-and-decisions).

## What works and should survive

- Canonical system typography, consistent Feather icons and restrained graphite controls already supply a coherent shared foundation.
- Measured foreground colors on white exceed the normal-text contrast floor. Exact ratios are recorded in the checklist; composed/tinted states still need measurement.
- `SalesTrend` preserves missing-value gaps, zero baseline, comparison marks, accessible date controls, supporting-record navigation and readable chart data. These are meaningful interactions to retain while simplifying composition.
- Existing draft, floor, actor and request-generation safeguards address real operational risks. Visual cleanup must preserve them.
- The immutable final export and existing performance/stability gate provide a release check. Focused affected checks improve iteration cost without redefining release acceptance.
